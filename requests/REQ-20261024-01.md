## 1. 何が変わったか（確定事項）

体制を二つに分けた。戦略室が計画し、Code が実装して公開する。

| | 戦略室 | Code |
|---|---|---|
| 担うこと | GTM 戦略の計画と判断材料、デイリーブラッシュアップ、依頼書の発行 | 実装、定期実行、push、パブリッシュ |
| 正の置き場 | 非公開のプロジェクト文書 | このリポジトリ |
| 書き込めるもの | プロジェクト文書のみ | このリポジトリ |

情報の流れは次の二本だけである。

- **戦略室から Code へ**：依頼書（本書のような .md）を ystskm が手で渡す。戦略室はこのリポジトリへ書き込めない（push 権限を持たない）。
- **Code から戦略室へ**：このリポジトリのみ。戦略室は作業の前に全ブランチと全 PR を取得し、前回からの差分を確認する。**リポジトリに置かれていない成果は、戦略室からは存在しないものとして扱われる。**

公開（パブリッシュ）は Code が定期実行で行う。

## 2. 更新してほしいファイル

### 2.1 `README.md`（改訂）

1. 冒頭の説明に、上記の体制（戦略室が依頼し、Code が実装・公開する）を1段落で加える。
2. 「運用」節の「`main` へのマージは代表が行う。マージが公開前の確認を兼ねる。」を、**定期実行による公開の手順**に置き換える。置き換え後の記述には、少なくとも次の三点を含める。
   - (a) 何が、いつ `main` に入り、公開されるか
   - (b) 公開の基準に照らした判定を、どの時点で行うか
   - (c) 公開を止める方法（定期実行の停止、取り下げの手順）
3. 「公開の基準」節は維持する。「置かないもの」の「個人名」の行に、**人物の指定表示は `ystskm` のみ許可**であることを明記する。「迷ったものは置かない。」は残す。
4. 「構成」の表に `requests/` と `reports/` を加える（2.3・2.4）。

### 2.2 `CLAUDE.md`（新設）

Code の単発セッションと定期実行が、毎回最初に読む作業規則として置く。最低限、次を含める。

- 体制の要約（本書第1節）。
- 作業開始時に `requests/` を確認し、`reports/` に完了の記録がない依頼から着手する。
- 表記の規則
  - 人物は `ystskm` または役割表記のみで書く。それ以外の個人名を書かない。
  - 見出し・本文・commit メッセージに絵文字や警告記号を使わない。
  - 事実・確定事項・仮説を混ぜない。仮説には〈仮説〉と付ける。
- 公開の基準は README を正とし、CLAUDE.md には写さない（置き場を二つにしない）。
- 作業の最後に `reports/` へ報告を残す（2.4）。
- **commit メッセージ末尾の `Claude-Session:` 行を必ず残す。**戦略室が成果物の作成元セッションを特定する手段はこの行しかない。

### 2.3 `requests/`（新設）

- 本書を `requests/REQ-20261024-01.md` として commit する。**この commit をもって受領とする。**戦略室は差分確認でこれを観測する。
- 依頼書の本文は書き換えない。進み具合は `reports/` に書く。

### 2.4 `reports/`（新設）

Code から戦略室への唯一の報告経路である。

- 単発・定期を問わず、1回の実行ごとに1ファイル。名前は `reports/YYYY-MM-DD-HHMM.md`（JST）。
- 書く項目
  - 起動元（単発か定期か、セッションの URL）
  - 対応した依頼番号
  - やったこと（commit と、変更したファイル）
  - 公開したもの（公開先の URL）
  - やらなかったこと・保留したことと、その理由
  - 戦略室または ystskm に確認したいこと
- 何も変更しなかった定期実行でも、1行の報告を残す（止まっていることと、何もなかったことを区別するため）。

### 2.5 定期実行の設定

- **Repository にこのリポジトリを指定して作成する。**戦略室の観測では、Repository の紐づけがないセッションはこのリポジトリへ push できない（2026-10-23〜24 に既存ブランチ・新規ブランチの両方で検証し、すべて HTTP 403 `not in this session's authorized repository set`）。一方、紐づけのある Code セッションからの push は成功している（`27dd6d4`）。紐づけはセッション単位で効く。
- 作成後に手動で1回発火し、`reports/` への報告が push されたことをもって設定完了とする。
